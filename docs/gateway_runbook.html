PHASE 1

Baseline — already written, verify it

app/backends.py, app/main.py, and the naive app/router.py are fully implemented. No code to write here — read them, run them, and be ready to defend them.

STEP 01

Read app/backends.py

READ

Open app/backends.py. Note SelfHostedBackend (latency 0.03s, error_rate 0.15, cost $0.0002) vs APIProviderBackend (latency 0.12s, error_rate 0.03, cost $0.004) — and the degraded flag that forces a 0.95 error rate when flipped on.

This asymmetry is the entire reason a fallback is worth building: a real self-hosted vLLM box behaves exactly like this — cheap and fast until it falls over under load — versus a paid API that's slower and pricier but steadier.

STEP 02

Read app/main.py

READ

Note the four routes: POST /gateway/generate, POST /admin/degrade/{name}, POST /admin/restore/{name}, GET /admin/status. The degrade/restore pair is how you'll simulate an outage later without killing a process.

STEP 03

Start the server

RUN

There's no if __name__ == "__main__" block in app/main.py, so python main.py won't do anything — app is a FastAPI object that a server has to host. Run it through uvicorn, from the repo root, in its own terminal window (leave it running):

powershell / cmd / bash — identical
cd resilient-model-gateway
pip install -r requirements.txt
uvicorn app.main:app --reload

Leave this running. Everything below hits it in a second terminal.

STEP 04

Call /gateway/generate and read the response

RUN

It's a POST with a JSON body — not a path like /gateway/generate/"question". FastAPI is validating the body against the GenerateRequest model, which only has a prompt field.

PowerShell
Invoke-RestMethod -Uri http://127.0.0.1:8000/gateway/generate -Method Post -ContentType "application/json" -Body '{"prompt": "what is the capital of France?"}'
bash / WSL / git-bash
curl -X POST http://127.0.0.1:8000/gateway/generate -H "Content-Type: application/json" -d '{"prompt": "what is the capital of France?"}'

Skip the bash block above if you're in native PowerShell — curl there is aliased to Invoke-WebRequest, whose -H/-d flags don't exist and will throw a parameter-binding error. That's PowerShell intercepting the command, not a bug in the project. The PowerShell block above already does the same thing correctly.

You'll get back something like {"answer": "[self_hosted] ok for: what is the capital...", "confidence": 0.83, "_served_by": "self_hosted", "_latency_ms": 41.2} — remember, the backend is a mock, so the "answer" is a canned string, not a real completion. Run it 10 times in a row and count the failures:

PowerShell — 10x
1..10 | ForEach-Object { try { Invoke-RestMethod -Uri http://127.0.0.1:8000/gateway/generate -Method Post -ContentType "application/json" -Body '{"prompt": "ping"}' | Out-Null; "ok" } catch { "FAILED" } }

Expect roughly 1 in 7 to fail outright (503) — that's self_hosted's 0.15 error_rate with zero retry logic yet. Now answer, out loud: why is confirming this naive, failure-prone baseline works before adding any resilience a meaningful checkpoint rather than a step you could skip? And once resilience exists, should main.py's bare except Exception: raise HTTPException(503, ...) stay that broad, or does it need to distinguish "genuinely no backend available" from other failures?

PHASE 2

The circuit breaker bug

AsyncTokenBucket, retry_with_backoff, and parse_llm_json in app/resilience.py are done. Only CircuitBreaker.record_failure() is broken. Prove the bug to yourself before you fix it.

STEP 05

Read the three working primitives

READ

In app/resilience.py, read AsyncTokenBucket (lock-protected refill-then-acquire), retry_with_backoff (full jitter: random.uniform(0, min(max_delay, base_delay * 2**attempt))), and parse_llm_json (direct parse → strip fences → strip trailing commas → give up). You'll wrap these around backend calls in Phase 3 — don't reinvent them.

STEP 06

Write scripts/debug_breaker.py

FIX

Create a new scratch file scripts/debug_breaker.py. In it: import CircuitBreaker from app.resilience, instantiate CircuitBreaker(failure_threshold=3, cooldown_seconds=1.0), call .record_failure() five times in a row, and after each call print the attempt number, .state, and .failure_count.

run it
python scripts/debug_breaker.py

Expected (correct) behavior: failure_count climbs 1, 2, 3 and state flips CLOSED→OPEN on the 3rd call. What you'll actually see: failure_count stuck at 0 forever, state never leaves CLOSED. That gap is the bug — go find the line responsible before reading Step 7.

STEP 07

Fix record_failure() in app/resilience.py

FIX

Inside record_failure(), the line self.failure_count on its own is a no-op expression — it reads the attribute and discards it, it never assigns anything. Change it to self.failure_count += 1.

STEP 08

Re-run debug_breaker.py to confirm the fix

RUN
run it again
python scripts/debug_breaker.py

Confirm failure_count now climbs 1→2→3 and state prints CircuitState.OPEN starting on the 3rd call. Before this fix, the breaker could only ever open via a failed HALF_OPEN probe — never from a run of repeated failures, which is the exact scenario your Phase 5 load test is supposed to demonstrate.

PHASE 3

Router upgrade — the centerpiece

The file's own docstring calls this "the most Sola-shaped thing you can be asked to sketch cold." Build the skeleton with me, then implement it yourself.

STEP 09

Build the upgraded generate() in app/router.py

BUILD

Ask for a TODO-commented skeleton, not filled-in code. Implement, per backend, in order: rate-limit against its AsyncTokenBucket; check its CircuitBreaker.allow_request() (if OPEN, skip straight to fallback without attempting a call); wrap the actual backend call in retry_with_backoff; on success call .record_success() and return, tagged with which backend served it and how many retries fired; on exhausted retries call .record_failure() and fall through — don't re-raise until the fallback has also failed.

Everything above must exist twice, independently, per backend — never a shared bucket or breaker. If one global breaker existed and the primary tripped it, the "healthy" fallback would get blocked too, which defeats the entire point of having a fallback.

STEP 10

Force-fail the primary and confirm fallback kicks in

RUN
PowerShell
Invoke-RestMethod -Uri http://127.0.0.1:8000/admin/degrade/self_hosted -Method Post
Invoke-RestMethod -Uri http://127.0.0.1:8000/gateway/generate -Method Post -ContentType "application/json" -Body '{"prompt": "test fallback"}'
Invoke-RestMethod -Uri http://127.0.0.1:8000/admin/restore/self_hosted -Method Post

The middle call should still return 200, with _served_by: "api_provider", even though self_hosted is fully degraded. If it 503s instead, your fallback path has a bug — check whether you're catching the retry-exhausted exception on primary before trying the fallback, not re-raising it immediately.

PHASE 4

Observability — the tiny dashboard

app/main.py already wires trace_store.summary_stats() into /admin/status. You're building what feeds it.

STEP 11

Design GatewaySpan's fields

READ

Open app/tracing.py. The dataclass is sketched but not required as-is. Before writing anything, answer: which fields let you reconstruct, after the fact, exactly when the breaker tripped and how the gateway responded at that moment? Why must circuit_state be captured at request time rather than read fresh later when you build the summary — what would you lose about "the breaker tripped mid-run" if you didn't?

STEP 12

Build TraceStore.record() and summary_stats()

BUILD

record() just appends to self.spans. summary_stats() is the real work: group spans by backend, and per backend return success rate, p50/p95 latency, current circuit state, and total cost. Design it with Phase 5's chart already in mind — it'll get called repeatedly over the course of a load test.

STEP 13

Verify /admin/status shows real numbers

RUN

Fire a handful of /gateway/generate calls, then:

PowerShell
Invoke-RestMethod -Uri http://127.0.0.1:8000/admin/status -Method Get | ConvertTo-Json -Depth 5

Confirm trace_summary shows both backends with a success rate, p50/p95, circuit_state, and cost — not the NotImplementedError path silently swallowing it.

PHASE 5

Load test & the failover chart

The concurrency harness in scripts/load_test.py is already built. Failure injection and the chart are the actual Day 4 deliverable.

STEP 14

Read the concurrency harness

READ

In scripts/load_test.py, read fire_one() and main(): a asyncio.Semaphore(CONCURRENCY) bounds how many requests are in flight at once, and each call's own try/except means one failed request can't crash asyncio.gather() for the whole batch.

STEP 15

Run the harness once, no failure injection yet

RUN
with the server still running
python scripts/load_test.py

This is your new baseline: with the resilience stack now in place, success rate should sit much closer to 200/200 than the roughly 85% you saw hammering the raw endpoint in Step 4 — retries are quietly absorbing self_hosted's transient failures. Worth noting explicitly when you talk through this project later.

STEP 16

Add failure injection + status polling

BUILD

Replace the single gather() call with logic that, partway through the run (tune DEGRADE_AT_REQUEST / RESTORE_AT_REQUEST for your machine), fires POST /admin/degrade/self_hosted, then later POST /admin/restore/self_hosted. Poll GET /admin/status at regular intervals throughout and store each snapshot with a timestamp — that time series is your chart's raw data.

STEP 17

Turn the results into a before/during/after chart

BUILD

matplotlib isn't a dependency yet:

add the dependency
pip install matplotlib

Plot latency and success rate over time (or over request index), with vertical lines or shaded regions marking the degrade and restore timestamps. This chart is the single artifact that proves — not claims — graceful degradation and recovery. It's also almost certainly what you'll be asked to walk through live.
