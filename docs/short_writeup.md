1) total latency budget across primary retries + fallback, when does "try harder on primary" cost more than "just fallback sooner"

once a backend is persistently degraded, every additional retry is spending real latency for close to zero marginal gain. this is especially costly with api_provider at 97% accuracy. from the plot, p50/p95 went 1.5x cumulative when primary degraded. in this case its worth it to stop the retries. this is why the circuit breaker exists -- correction after re-checking: it DOES trigger, reliably (10/10 reruns of the load test tripped it, 1-5 times per run). the original "it never triggered" note was wrong -- it came from reasoning about a single sequential request (failure_count resetting on occasional retry-recovered successes), which doesn't hold once concurrent requests are failing out close together in time. see README.md / docs/architecture.md for the corrected version, plus a second bug the correction turned up (now fixed in app/resilience.py lines 94-127): record_success() was clobbering a legitimate OPEN state via a race with a concurrent failure, skipping HALF_OPEN entirely. Verified fixed across 5 reruns -- zero bypasses post-fix.

2) how would i route by request type instead of always trying primary first?

if we add a request_type into the generate call, we can occassionally traffic certain calls to get api_provider first. the more complex part is determining the request_type. the caller should determine this instead of inferring from the prompt content. in temrs of the caller determining, it can be an option in the post request, or it can be determined by some caller categorization.
